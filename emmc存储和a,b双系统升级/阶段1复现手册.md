**i.MX6ULL eMMC A/B 双系统**

阶段一：安全分区、启动文件与 A/B 启动复现指南

适用环境：正点原子 i.MX6ULL / U-Boot 2016 系列 / Linux 4.1.15 / eMMC /
TFTP + NFS

**本文用途：** 用于在同一块板或新 eMMC
上，从零重建阶段一；按顺序执行并完成文末验收，才能判定阶段一完成。

阶段一的目标不是 OTA，也不是自动回滚。它只完成可靠升级的地基：eMMC
分区布局固定、A/B 两套根文件系统可独立存在、U-Boot
能按槽位加载对应内核/设备树并把 root= 指向对应根分区。Bootcount
与连续失败自动回滚属于后续阶段。

# **1. 阶段一完成标准**

只有下面四项全部通过，才算阶段一真正完成。此前出现过的“内核已启动但
rootfs panic”说明：启动分区恢复成功不等于 A 槽根文件系统已经可启动。

| **验收项** | **必须看到的结果**                                                                             |
|------------|------------------------------------------------------------------------------------------------|
| 分区布局   | mmc part / fdisk -l 显示 p1=128 MiB FAT32，p2=1 GiB rootfs_A，p3=1 GiB rootfs_B，p4=数据分区。 |
| A 槽启动   | U-Boot 读取 zImage_A 与 imx6ull-alientek-emmc_A.dtb；Linux 的 / 挂载在 /dev/mmcblk1p2。        |
| B 槽启动   | U-Boot 读取 zImage_B 与 imx6ull-alientek-emmc_B.dtb；Linux 的 / 挂载在 /dev/mmcblk1p3。        |
| NFS 救援   | 即使 eMMC 启动文件或 rootfs 出错，也能通过 TFTP 内核 + DTB、NFS 根文件系统进入系统修复。       |

**当前项目提醒：** 若从 eMMC 启动时出现 unknown-block(179,10)，其对应
/dev/mmcblk1p2。先执行第 9 节的只读检查；不能仅因为能从 NFS 进入 Linux
就判定 A 槽 rootfs 已完成。

# **2. 固定环境与设备编号**

| **项目**        | **本项目固定值**                            |
|-----------------|---------------------------------------------|
| U-Boot 中 eMMC  | mmc 1（mmc list 会显示 FSL_SDHC: 1 (eMMC)） |
| Linux 中 eMMC   | /dev/mmcblk1                                |
| U-Boot 加载分区 | mmc 1:1，即 FAT32 启动分区 p1               |
| TFTP 服务器     | 192.168.3.66                                |
| 板端临时 IP     | 192.168.3.50                                |
| NFS 根目录      | /home/huanyu/linux/rootfs_gst               |
| 串口            | ttymxc0，115200                             |

**重要：** U-Boot 的 mmc 设备编号和 Linux 的 /dev/mmcblk
编号不是同一套规则。本项目必须牢记：U-Boot 写/读 eMMC 用 mmc 1；Linux
操作 eMMC 用 /dev/mmcblk1。

# **3. eMMC 目标分区布局**

分区表为 DOS/MBR。p1 与 U-Boot 镜像所在的裸扇区区域分离：p1 从扇区 20480
开始，因此在 p1 之前保留了启动镜像空间。

| **分区** | **起始扇区** | **扇区数** | **容量**    | **类型/用途**                      | **标签** |
|----------|--------------|------------|-------------|------------------------------------|----------|
| p1       | 20480        | 262144     | 128 MiB     | FAT32，内核、DTB、boot.scr（可选） | \-       |
| p2       | 282624       | 2097152    | 1 GiB       | ext4，Rootfs A                     | rootfs_a |
| p3       | 2379776      | 2097152    | 1 GiB       | ext4，Rootfs B                     | rootfs_b |
| p4       | 4476928      | 10792960   | 约 5.15 GiB | ext4，数据、日志、升级缓存         | data     |

**风险控制：** 重新分区会清空 eMMC 上的全部分区数据。只允许在已从 SD/NFS
启动、并且确定无需保留 p2/p3/p4 内容时执行。已有正确分区表时，跳过第 4
节。

# **4. 从零建立分区表（仅全新 eMMC）**

在 NFS Linux 中执行。先确认设备绝对是 /dev/mmcblk1，再进入
fdisk。下列数值必须与上表一致。

fdisk -l /dev/mmcblk1  
fdisk /dev/mmcblk1

在 fdisk 内依次创建 DOS 分区表和四个主分区：p1 从 20480 开始、大小
+128M、类型 c；p2 从 282624 开始、大小 +1G、类型 83；p3 从 2379776
开始、大小 +1G、类型 83；p4 从 4476928 开始、使用剩余全部空间、类型
83。写入前先按 p 再次核对。

\# 写入后必须重新读取并核对  
fdisk -l /dev/mmcblk1  
blkid /dev/mmcblk1p1 /dev/mmcblk1p2 /dev/mmcblk1p3 /dev/mmcblk1p4

# **5. 格式化与根文件系统准备**

所有格式化操作只能在 NFS/SD 临时系统中执行，绝不能格式化当前正在作为 /
使用的根分区。Buildroot 中若没有 mkfs.ext4，应先把已构建的 e2fsprogs
工具安装进 NFS 根文件系统；FAT 分区使用本项目已确认存在的 mkdosfs。

\# 仅在确认分区可被清空后执行  
mkdosfs -F 32 /dev/mmcblk1p1  
mkfs.ext4 -F -L rootfs_a /dev/mmcblk1p2  
mkfs.ext4 -F -L rootfs_b /dev/mmcblk1p3  
mkfs.ext4 -F -L data /dev/mmcblk1p4

mkdir -p /mnt/rootfs_a /mnt/rootfs_b /mnt/data  
mount /dev/mmcblk1p2 /mnt/rootfs_a  
mount /dev/mmcblk1p3 /mnt/rootfs_b  
mount /dev/mmcblk1p4 /mnt/data  
blkid /dev/mmcblk1p2 /dev/mmcblk1p3 /dev/mmcblk1p4

推荐在 Ubuntu 主机上复制 NFS 根目录，而不是在板端把当前 /
直接打包。这样不会把 proc、sys、临时挂载点等伪文件系统误带入目标
rootfs。以下命令分别复制到 A、B：

\# Ubuntu 主机执行；/mnt/rootfs_a、/mnt/rootfs_b 为已挂载的目标分区  
sudo tar --numeric-owner -C /home/huanyu/linux/rootfs_gst -cpf - . \|
\\  
+ sudo tar --numeric-owner -C /mnt/rootfs_a -xpf -  
sudo tar --numeric-owner -C /home/huanyu/linux/rootfs_gst -cpf - . \|
\\  
+ sudo tar --numeric-owner -C /mnt/rootfs_b -xpf -  
sync

**复制后检查：** 两个槽位均应至少有
bin、sbin、etc、lib、usr、dev、proc、sys、tmp、root 等目录；tmp 应为
1777。

# **6. p1 启动文件：A/B 命名规则**

U-Boot 不直接从裸扇区读取 zImage/DTB，而是从 p1 的 FAT32
文件系统按文件名读取。因此内核和设备树必须通过 FAT
文件系统复制进去，不能用 mmc write 把它们写到 0x2。

| **槽位** | **内核文件** | **设备树文件**              | **Linux 根分区** |
|----------|--------------|-----------------------------|------------------|
| A        | zImage_A     | imx6ull-alientek-emmc_A.dtb | /dev/mmcblk1p2   |
| B        | zImage_B     | imx6ull-alientek-emmc_B.dtb | /dev/mmcblk1p3   |

板端在 NFS Linux 下，可从 TFTP 下载正式源文件再复制为 A/B
命名。首次只部署 A 也可以，但阶段一验收必须补齐 B。

cd /tmp  
tftp -g -r zImage -l zImage 192.168.3.66  
tftp -g -r imx6ull-alientek-emmc.dtb -l imx6ull-alientek-emmc.dtb
192.168.3.66  
  
mkdir -p /tmp/emmc_p1  
mount /dev/mmcblk1p1 /tmp/emmc_p1  
cp /tmp/zImage /tmp/emmc_p1/zImage_A  
cp /tmp/zImage /tmp/emmc_p1/zImage_B  
cp /tmp/imx6ull-alientek-emmc.dtb
/tmp/emmc_p1/imx6ull-alientek-emmc_A.dtb  
cp /tmp/imx6ull-alientek-emmc.dtb
/tmp/emmc_p1/imx6ull-alientek-emmc_B.dtb  
sync  
ls -lh /tmp/emmc_p1  
umount /tmp/emmc_p1

**禁止命令：** mmc write \${loadaddr} 0x2 \${bootblkcnt}
只能用于刚刚通过 TFTP 下载的 u-boot.imx。若当前 filesize 来自 zImage（约
6.5 MiB）或 DTB，写入会覆盖启动区域甚至破坏 p1 FAT 文件系统。

# **7. U-Boot：配置 A 槽启动**

先在 U-Boot 提示符执行 mmc dev 1 和 fatls mmc 1:1，确保 p1
可读且文件名正确。现有 bootcmd 已通过 loadimage/mmcboot
启动时，只需设置以下变量，不要随意覆盖已有 bootcmd。

mmc dev 1  
fatls mmc 1:1  
  
setenv slot A  
setenv mmcdev 1  
setenv mmcpart 1  
setenv image zImage_A  
setenv fdt_file imx6ull-alientek-emmc_A.dtb  
setenv rootpart /dev/mmcblk1p2  
setenv boot_fdt yes  
setenv mmcargs 'setenv bootargs console=ttymxc0,115200 root=\${rootpart}
rootwait rw'  
saveenv  
printenv slot mmcdev mmcpart image fdt_file rootpart mmcargs boot_fdt  
reset

正常日志应包括：reading zImage_A、Booting from mmc ...、reading
imx6ull-alientek-emmc_A.dtb。进入 Linux 后 / 的设备必须是 mmcblk1p2。

# **8. U-Boot：切换到 B 槽与切回 A 槽**

阶段一的切换采用一次性环境变量切换。执行 saveenv
后才会在复位后保留；未做健康确认与自动回滚逻辑，这部分属于阶段二/三。

## **8.1 切换到 B**

setenv slot B  
setenv image zImage_B  
setenv fdt_file imx6ull-alientek-emmc_B.dtb  
setenv rootpart /dev/mmcblk1p3  
saveenv  
reset

## **8.2 切回 A**

setenv slot A  
setenv image zImage_A  
setenv fdt_file imx6ull-alientek-emmc_A.dtb  
setenv rootpart /dev/mmcblk1p2  
saveenv  
reset

**变量解释：** image 决定从 p1 读哪个 zImage；fdt_file 决定从 p1 读哪个
DTB；rootpart 决定 kernel bootargs 中 root=
的值。三者必须成对切换，不能只改 image。

# **9. 验收脚本与故障定位**

## **9.1 U-Boot 侧快速验收**

mmc dev 1  
mmc part  
fatls mmc 1:1  
printenv slot image fdt_file rootpart mmcargs  
  
\# 只验证文件可读，不会写 eMMC  
fatload mmc 1:1 \${loadaddr} zImage_A  
fatload mmc 1:1 \${fdt_addr} imx6ull-alientek-emmc_A.dtb

## **9.2 Linux 侧验收**

cat /proc/cmdline  
mount \| grep ' on / '  
blkid /dev/mmcblk1p2 /dev/mmcblk1p3  
ls -ld /bin /etc /sbin /usr /tmp  
  
\# 从 A 启动时，只读检查 B；从 B 启动时，把 p2/p3 对调  
mkdir -p /tmp/rootfs_other  
mount -t ext4 -o ro /dev/mmcblk1p3 /tmp/rootfs_other  
ls -la /tmp/rootfs_other  
umount /tmp/rootfs_other

| **现象**                                    | **根因**                                                  | **处理**                                                                |
|---------------------------------------------|-----------------------------------------------------------|-------------------------------------------------------------------------|
| fatls mmc 1:1: Unrecognized filesystem type | p1 的 FAT 文件系统损坏或被裸写覆盖                        | 从 NFS 启动；mkdosfs -F 32 /dev/mmcblk1p1；重新复制 A/B zImage 与 DTB。 |
| Unable to read file zImage_A / DTB_A        | p1 文件名与 image/fdt_file 不一致                         | fatls 查看真实文件名；统一成 A/B 命名或修改对应变量。                   |
| Bad Linux ARM zImage magic                  | 内核没有成功加载，内存中是旧数据                          | 先检查 fatload 是否成功；不要继续 bootz 无效地址。                      |
| unknown-block(179,10)                       | 内核正挂载 /dev/mmcblk1p2，但 p2 没有有效 ext4 根文件系统 | NFS 启动后 blkid、只读 mount p2；必要时重新格式化并复制 rootfs_A。      |
| 网络启动报 ethaddr/ipaddr/serverip 未设置   | 临时网络环境变量不存在                                    | 按第 10 节临时设置；不要依赖 netboot 修复 eMMC。                        |

# **10. NFS 救援启动（不写 eMMC）**

当 p1 或 rootfs 损坏时，在 U-Boot 中用以下命令临时启动。它只通过网络加载
zImage/DTB 并把根文件系统挂到 NFS，不会修改 eMMC。MAC
地址必须替换为板卡实际地址；以下地址仅用于当前实验网段。

setenv ethaddr 02:12:34:56:78:9a  
setenv ipaddr 192.168.3.50  
setenv serverip 192.168.3.66  
setenv netmask 255.255.255.0  
tftpboot \${loadaddr} zImage  
tftpboot \${fdt_addr} imx6ull-alientek-emmc.dtb  
setenv bootargs 'console=ttymxc0,115200 root=/dev/nfs rw
nfsroot=192.168.3.66:/home/huanyu/linux/rootfs_gst,v3,tcp
ip=192.168.3.50:192.168.3.66:192.168.3.1:255.255.255.0::eth0:off'  
bootz \${loadaddr} - \${fdt_addr}

**不要保存临时网络变量：** 除非确认 MAC/IP 的规划无误，否则上述
ethaddr、ipaddr、serverip 不执行 saveenv。ethaddr
写错会给后续网络调试制造新问题。

# **11. 阶段一收尾检查清单**

- p1/p2/p3/p4 的扇区起点、大小与第 3 节完全一致。

- p1 可 fatls，且同时存在
  zImage_A、zImage_B、imx6ull-alientek-emmc_A.dtb、imx6ull-alientek-emmc_B.dtb。

- p2 与 p3 均显示 TYPE="ext4"，标签分别为 rootfs_a、rootfs_b。

- 从 A 槽启动后，mount \| grep ' on / ' 显示 /dev/mmcblk1p2 on /。

- 从 B 槽启动后，mount \| grep ' on / ' 显示 /dev/mmcblk1p3 on /。

- A、B 至少互相切换启动一次，且另一个槽位能只读挂载检查。

- 已保存一份 NFS 救援启动命令，不依赖 eMMC 内文件也能进入 Linux。

- 确认后才进入阶段二：只升级非运行槽位；阶段三再接入 bootcount
  与失败回滚。

# **12. 经验结论：本次故障为何发生、以后如何避免**

本次恢复过程中，MBR 分区表始终存在，但 p1 FAT 文件系统被误覆盖，因此
U-Boot 不能识别文件系统，也读取不到 zImage/DTB。重新 mkdosfs 并恢复 A
槽启动文件后，U-Boot 能重新加载内核。随后出现的 VFS panic
则是另一个层面的问题：内核已经找到 mmcblk1p2，却无法把它作为 rootfs
挂载。

最重要的操作边界是：U-Boot
镜像属于固定裸扇区写入；内核、设备树、升级包属于 p1
文件系统文件；根文件系统属于 p2/p3 的 ext4
文件系统。三类数据的写入方式不能混用。

**最终原则：** 每次 mmc write 之前必须同时确认“当前 RAM
中是什么文件、目标起始扇区是什么、块数由哪个 filesize
计算”。不确定时停止写入，先用 mmc part、fatls、printenv 和 md.b
做只读确认。
